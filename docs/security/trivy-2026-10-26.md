records have a fixed version; none of the Debian records has a fixed Trixie
version in this scan. Six image records are fixable HIGH/CRITICAL findings.
The current lockfile has 10 records: 2 CRITICAL, 4 HIGH and 4 MEDIUM, all fixable.

Presence/version matching does not prove exploitability. In particular, source
package matching can flag libraries for a vulnerability in another executable
from that source. No exploit, live deployment or runtime hardening audit was
performed. The absence of findings for CPython or native libraries bundled in
wheels is not proof that those components have no vulnerabilities.

## Remediation options

Scores express the balance of security benefit, effort and compatibility for
this application: 10 is best. The changes below are proposals; this task adds
scanning and evidence without changing dependencies or runtime contents.

### 1. Targeted application dependency updates — 10/10

| Package | Installed | Minimum fixed version in report | Findings |
| --- | --- | --- | --- |
| anyio | 4.13.0 | 4.14.2 | CVE-2026-63374 (CRITICAL), CVE-2026-64847 (MEDIUM) |
| certifi | 2026.4.22 | 2026.10.19 | GHSA-6q48-6c7w-9gw2 (CRITICAL) |
| idna | 3.13 | 3.15 | CVE-2026-45409 (MEDIUM) |
| pydantic-settings | 2.14.0 | 2.14.2 | GHSA-4xgf-cpjx-pc3j (MEDIUM) |

Update these entries through the dependency resolver, review the lockfile diff,
run the existing suite (including PostgreSQL), then build and scan a new patch
release. These are minimum fixed versions from the captured database, not a
guarantee that those versions are free of other advisories.

AnyIO's critical finding concerns TLS hostname encoding; certifi retains roots
associated with compromised intermediate keys. Both are relevant to reviewing
outbound HTTPS trust. The AnyIO process-pool finding and pydantic-settings nested
secrets finding depend on feature use; current source search found no use of
process-pool APIs or `NestedSecretsSettingsSource`. Updating is still preferable
to carrying old versions. Preserve TLS verification and test connections with
the deployment's CA configuration.

### 2. Remove pip from the final runtime image — 9/10

The final image contains pip 26.2.2. Reading
`usr/local/lib/python3.14/site-packages/pip/_vendor/vendor.txt` directly from
image layer `sha256:2cb672340c81d54eae68bd73635134ad5ede9da3664d3d638e94bae1666adae8`
confirmed these embedded versions:

| Embedded package | Installed | Findings | Fixed version(s) |
| --- | --- | --- | --- |
| msgpack | 1.1.2 | GHSA-6v7p-g79w-8964 (HIGH) | 1.2.1 |
| setuptools | 70.3.0 | CVE-2025-47273 (HIGH), CVE-2026-59890 (MEDIUM), GHSA-xmj3-9gf7-h52w (LOW) | 78.1.1, 83.0.0, 84.1.0 respectively |
| urllib3 | 2.7.0 | CVE-2026-97687 and CVE-2026-97689 (HIGH), CVE-2026-97688 (MEDIUM) | 2.8.0 |

These seven records come from pip's vendored dependencies, not seven additional
application dependency entries. Installing a separate newer urllib3 or
setuptools does not replace pip's embedded copies. The runtime command uses the
already-built virtual environment and does not install packages. Keep pip/uv in
the builder and remove the base image's pip from the final stage, then verify
startup, version output, PostgreSQL and TLS before rescanning. Expected benefit:
remove these seven records, including four HIGH records; confirm with a new scan.

Alternative: retain pip but upgrade to an upstream release whose bundled
versions are fixed — 6/10. That release's vendoring list must be checked; no
specific pip version has been verified as resolving all seven records here.

### 3. Update development urllib3 — 9/10

The current `uv.lock` contains urllib3 2.6.3, brought in through development
dependencies. It is not the same copy as pip's embedded urllib3 2.7.0.
Upgrade the lockfile to a compatible version at least 2.8.0. This addresses
CVE-2026-44431 and CVE-2026-44432 (fixed in 2.7.0), plus CVE-2026-97687,
CVE-2026-97689 and CVE-2026-97688 (fixed in 2.8.0). Validate testcontainers and
Docker-client tests. This fixes the dependency gate, not the runtime pip copy.

### 4. Triage remaining Debian HIGH findings — 7/10

| Advisory group | Source / reported packages | Action |
| --- | --- | --- |
| CVE-2026-76642, CVE-2026-78408, CVE-2026-78409, CVE-2026-78410 | util-linux; repeated across 9 binary packages | Inspect affected mount/nsenter helpers, their privilege requirements and deployed capabilities. Await a Trixie fix or evaluate a maintained minimal runtime that omits the affected tools. |
| CVE-2025-69720 | ncurses; 4 binary packages | Advisory concerns the infocmp executable. Verify whether the affected executable and attack path exist; do not infer exploitable Python readline from the library package label alone. |
| CVE-2026-16742 | libsystemd0, libudev1 | Advisory concerns systemd-homed. Verify component absence before recording a not-affected justification. |
| CVE-2026-54369 | libacl1 | Review ACL API use and symlink/privilege preconditions; retain isolation and follow vendor patches. |
| CVE-2026-9538 | perl-base | Review Archive::Tar presence and untrusted archive processing; Debian reports the fix as deferred. |

These are eight distinct HIGH advisories across 44 Debian binary-package
records. Do not blindly remove Essential packages or import Debian sid packages
into Trixie. Debian tracks several of these as minor/no-dsa even though Trivy's
severity is HIGH. Use narrowly justified VEX/exception records only after
checking actual image contents and deployment preconditions, with review dates.
No suppressions were added by this task.

An ordinary rebuild/apt upgrade alone scores 4/10 for the captured Debian
findings: it is useful maintenance but there is no fixed Trixie version in the
captured report. Migration to another maintained minimal runtime scores 5/10
until a candidate is built, tested and compared by scan; a smaller CVE count
alone does not establish lower application risk.

## Recommended sequence

1. Update the four application dependencies and development urllib3.
2. Remove pip from runtime and test the resulting image.
3. Publish a new patch version; preserve immutable v0.3.0 and its digest.
4. Review the remaining Debian findings against actual components and runtime
   privileges. Rescan the new image and retain the comparison.

The new CI configuration scans dependencies before packaging. Its image gate
runs after Docker Hub publication and before GitLab Release creation; a failed
image gate does not retract an already-published image tag.
